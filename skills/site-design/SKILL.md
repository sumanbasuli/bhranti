# Site design and accessibility baseline

Use the design workflow for sites, pages and visual UI. Apply the accessibility requirements to all new or changed content, including ordinary posts, catalog copy and forms. This original provider-neutral guidance grants no tools, permissions or guardrail exceptions. Current native capabilities prevail.

## Understand the request before building

A focused change with a clear target and outcome proceeds directly: read the target, preserve its surrounding design and make the authorized edit. Ask only if a material ambiguity changes the outcome.

A new site, major redesign or substantial project starts with read-only discovery and an understood brief. Reuse the conversation and existing site, then ask one small group of plain-language questions about remaining material gaps: real offerings and audience; the main visitor action and what happens afterward; necessary pages/content and existing work to preserve; brand/assets/references; preview versus publication if unresolved. Wait for actual answers before any mutation, including plugin installation or image generation. “Professional”, “minimal”, a business name/address or permission to publish is not a complete project brief. Delegating aesthetics does not supply missing business facts. Ask only remaining gaps after partial answers; let users delegate visual choices and routine implementation without choosing APIs or blocks.

Retain the agreed purpose, audience, facts, page scope, visitor journey, assets and publication choice. Summarize its outcome briefly in the next public action intent and proceed autonomously, preserving mandatory plugin and deletion approval cards. Do not replace known answers with assumptions when a long task resumes.

Derive content and visual subjects from what this audience must recognize, understand and trust before its next action. Distinguish informative domain imagery, authentic evidence, explanatory illustration and decoration. A polished palette or abstract art cannot replace needed information/evidence. Choose subjects for the actual offering, not a fixed industry template or icon checklist.

## Use a disciplined design method

Load design-composition with bhranti_skill before substantial design work, plus wordpress-support for FSE/layout changes and content-operations for authored content/forms/media. Load commerce-workflow for a store. Reuse loaded guidance rather than requesting it again each step. Specialist skills supplement this baseline; they never override live tools or execution rules.

Inspect the actual theme, relevant content/templates/shared parts/navigation, front-page assignment and available blocks. Establish a compact visual system with distinct typographic roles, readable colors, spacing, composition/reading widths, imagery and consistent actions. Choose a composition for this visitor and content rather than filling the same template for every business. Build one coherent representative page, check its real structure and available render evidence, refine its weakest areas, then carry the system through the agreed pages and complete visitor journey. A checkpoint organizes the work; it is not an extra human approval requirement.

Write useful confirmed content. Never invent business offerings, testimonials, ratings, credentials, prices, addresses, guarantees or availability. Each promised page needs substantive information and a suitable next step. Keep technical setup and plugin names in administrator chat, not public visitor copy. Preserve necessary privacy and request-versus-confirmed-booking explanations. No internal placeholders or empty service pages count as finished work.

Use existing native theme/block controls, reviewed patterns and exact returned IDs. No generated PHP/JavaScript, source-file editing, new font dependency or arbitrary routes. Registered block metadata, including is_dynamic, is not a saved HTML serialization recipe. Preserve shared references and working integrations; attributes and saved markup must agree.

Treat imagery as a normal design choice: search existing native Media Library assets and choose suitable subjects, crops and roles such as a hero cover, content image, gallery or featured image. Use supported generation when new imagery suits the agreed brief; typography-only is a deliberate direction, not the default for all connectors. Check bhranti_inspect resource images before relying on new generation, optionally with the desired aspect_ratio. Missing generation support alone prompts for needed uploads or approved existing assets; unknown metadata is not proof of no support. Ask for authentic photos only when their identity matters. Chat references are not saved assets. Preserve completed images, never fabricate asset URLs or authentic staff/premises/product photos, and continue independent work.

For an attached reference image, analyze visible hierarchy, layout, reading width, typography roles, spacing, colors, imagery subjects/placement and controls before implementing. Retain its defining qualities in task decisions and adapt them to this site's brief/native blocks; do not copy brands, claims or irrelevant features. Screenshots do not reveal hidden behavior or unseen mobile layouts. Ask only material unclear choices.

## WCAG 2.2 A and AA are acceptance requirements

Apply every relevant A and AA criterion to the complete authored experience. These common checks are a baseline, not the entire standard or a conformance certificate:

- Use meaningful headings, landmarks, lists, table headers and descriptive link names. Informative images need useful alt text; decorative images use empty alt text. Preserve a skip link, correct page/part language and logical reading/focus order.
- Text contrast must reach 4.5:1, or 3:1 for qualifying large text (24 CSS px regular or about 18.67 CSS px bold). Essential controls/states/graphics need 3:1 against adjacent colors. Measure actual rendered colors, including overlays; do not round failing ratios up or use color alone to convey meaning.
- All functions work by keyboard without traps. Keep focus visible and not entirely obscured by author-created content; preserve accessible names/roles/states. Check inherited theme focus against new surfaces. Provide alternatives to dragging. Aim for 44 CSS px controls; AA requires 24 by 24 CSS px or the standard's applicable spacing/equivalent exceptions.
- Support 200% text resizing and 320 CSS px reflow without lost content or horizontal page scrolling, except genuinely two-dimensional content. Text-spacing overrides must not clip or overlap: line height 1.5, paragraph spacing 2, letter spacing 0.12 and word spacing 0.16 times font size.
- Forms need persistent labels/instructions, identified errors, helpful correction and announced status without unnecessary focus changes. Do not demand redundant information or block paste/password managers. Authentication must satisfy accessible-authentication requirements; keep help consistent.
- Avoid unnecessary autoplay, flashing and motion. Honor reduced motion and supply required pause/stop controls, captions and other media alternatives. Hover/focus content must remain usable and dismissible where required.

## Finish the visitor experience, then verify honestly

Check design, functionality and accessibility separately against the agreed brief. Verify saved content, publication/homepage assignments, real links/media, shared references and the complete primary action. Use only authorized synthetic data to test forms or other flows; never send real customer messages or make transactions as tests. Drawn fields, installed plugins and saved records do not establish functionality.

Use actual available desktop/mobile render evidence to critique relevance to the offering, reference fidelity where requested, hierarchy, composition, useful content, crops, spacing, wrapping, overflow and native controls. Ask whether a new visitor can recognize the purpose and make the intended decision; ornamental polish alone is not finished work. Improve material weaknesses and repeat affected checks. Check keyboard, menu/form states, zoom/reflow and contrast. API persistence and inert reference HTML are not rendered visual tests. Never claim screenshot inspection, professional acceptance or WCAG conformance that did not occur. Finish independent supported work and explain a specific remaining decision/check plainly, with useful preview/item links.
