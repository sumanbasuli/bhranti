# Bhranti

A WordPress-aware assistant accessed as **Bhranti** in the WordPress admin bar. Its chat sidebar uses native WordPress colors and stays alongside the current editor or site page. It uses the site's native WordPress AI Client and Settings → Connectors, with no provider settings or credentials inside this plugin.

## Working behavior

- Private conversations owned by the requesting administrator, with recent history and native notices.
- Persisted tasks continue through native WordPress scheduling after the panel or browser closes. The configurable task limit defaults to 128 steps (12–1,000). Each prepared action shows its intent, native API operation and affected item before execution; pending native requests show elapsed time.
- Search and inspection through reviewed WordPress REST endpoints and the native WordPress.org plugin directory; site, rendered current-page HTML/text, selected Gutenberg blocks and optional browser-chosen screenshot context.
- Native AI image generation saves validated raster images to Media Library as Bhranti, with descriptive alt text and traceable logs. Images remain in the library after a page-content rollback.
- Reviewed content and settings operations executed as a dedicated managed **Bhranti** WordPress user, limited by both that user's and the requesting administrator's permissions. Writes are blocked when native filtering under those permissions would alter existing markup.
- Settings provides enforced switches for content editing/publishing, Trash, comments, media, navigation, design, site settings and plugin installation/activation/deletion. Routine actions default on; plugin deletion defaults off.
- Reviewed plugin operations use native WordPress APIs and WordPress.org directory packages, with temporary actor capabilities scoped to the specific core call. Plugin deletion requires a concrete human approval and warns about permanent uninstall data loss. Activation status can be restored when unchanged; lifecycle hook effects cannot. Reinstalling a deleted plugin restores its directory package, not deleted data.
- Deletion always pauses for a human confirmation button. Approvals are stored server-side, expire after ten minutes, bind to the specific item state, and cannot be reused. Permanent content deletion is blocked; opted-in native plugin uninstall is the documented exception.
- Supported changes retain seven-day rollback snapshots. Rollback checks the current item against the saved result before restoring; it refuses to overwrite later edits. It restores supported WordPress data, not emails, webhooks or other third-party side effects.
- A separate Bhranti → Logs screen retains paginated activity records with requester and actor usernames/IDs. The chat groups completed actions in expandable rows with their outcome, affected item and available rollback. Failures and human approvals stay visible; real task status and Stop stay above the composer.
- Bhranti → Settings uses native WordPress React cards for system prompts, additional guardrails, and named agents with pasted `agent.md` and attached `skill.md` documents. Select an agent from the chat menu. Each run keeps the configuration it started with; later settings changes apply to new requests. Markdown is instruction text and is never executed as code. Built-in API permissions and confirmation checks cannot be disabled by these settings.
- Native privacy export and erasure; deletion of conversations removes their private state and rollback records. Uninstall removes workspace data and revokes the managed account's elevated role while preserving normal site content and authorship.

The managed account is created on first use, with a random password and blocked interactive/application-password login. It is a traceable executing identity, not a second administrator login. Bhranti never edits arbitrary source code, WordPress core, theme/plugin source code, accounts, roles, credentials or security settings. It can manage directory plugins through its reviewed native plugin tool when the administrator enables those actions. Only reviewed core REST controllers are reachable; third-party route support requires an explicit reviewed adapter. Existing-template deletion is blocked because WordPress can resolve a deleted customization to its theme fallback, preventing reliable restoration. This is not a universal WordPress executor.

## Native AI and privacy

Configure an existing text provider in **Settings → Connectors**. Sending a request shares your message, up to 12 recent conversation messages, basic site information, attached rendered-page HTML/text, selected-block context, explicitly captured screenshots, selected agent and skill instructions, image-generation prompts, and relevant site content/tool results through the native WordPress AI Client. The provider's terms apply. Bhranti stores no connector credentials and adds no telemetry or internal connection preferences. Native connector approvals remain authoritative. Site-wide agent settings remain until replaced or uninstalled; a conversation's configuration snapshots are included in its private data export and erasure.

Background continuation requires site traffic or a configured native WordPress cron runner. Open editors pause background writes; dirty tabs remain protected until saved/discarded, or explicitly resumed after their marker expires. Clean editor tabs permit foreground execution without navigation, reload or injected blocks. The sidebar does not automatically open generated images. Deletion approval always requires the human button. Per-tab protection stores only a UUID, editor/dirty flags and expiry, with native privacy cleanup.

The installed native AI transport returns completed replies; Bhranti does not simulate token streaming. Workspace, conversation and Settings reads have a 20-second timeout with Retry, while action requests retain their native execution timeout. Opening saved history never replays historical navigation events. The main WordPress frame is rounded; the outer chat panel is square. Action planning uses an explicit native strict JSON schema and a scoped 120-second request timeout (180 seconds for image generation), and a failed plan gets one bounded planning recovery without executing it. Native provider failure codes are logged without raw error payloads.

## Development and verification

Requires WordPress 7.0+ and PHP 7.4+. Runtime assets use WordPress core React components for Settings and local JavaScript/CSS for the sidebar; no frontend build is required. See `AGENTS.md` for the user's persistent project requirements.

Run syntax checks, WordPress Coding Standards and the official Plugin Check against the distribution. Real WordPress tests in `tests/integration.php`, `tests/actions.php`, `tests/settings.php`, `tests/permissions.php` and `tests/plugins.php` run only with `BHRANTI_TEST_WP_ROOT` and `BHRANTI_TEST_ALLOW_MUTATION=1`, and reject any site other than `https://bhranti.wp.local/`. They use a local fake provider and uniquely marked disposable records; they must never change preexisting site content.

`php tests/product-ux.php` exercises the actual backend classes with in-memory storage and identity seams, without loading the site or making DB, HTTP or AI requests. It verifies that Resume preserves source history, resolved failures remain collapsed across later requests, and refresh metadata distinguishes successful reads, writes, images and rollbacks without treating rejected or pending actions as completed changes. `php tests/ai-timeout.php` verifies scoped native timeout hooks without HTTP or AI requests. Set `BHRANTI_TEST_WP_ROOT` when core is installed elsewhere.

Source files and tests are excluded from the runtime ZIP where appropriate. Directory acceptance still requires human review; automated passes are not an approval guarantee.

The sidebar uses `#1E1E1E` with WordPress palette controls and locally bundled solid MIT Bootstrap Icons, with smaller artwork inside comfortable click targets. Chats, New chat and Settings are direct header controls; each chat retains its own unsent draft in tab session storage. Chat search, expanded action details and keyboard focus survive updates. The inline Jump to latest control appears while reviewing older messages. Unchanged polls skip redraws; changed responses retain the connected conversation log, unchanged rows and the composer textarea. Open state persists across admin navigation until closed. Screenshot capture uses the browser sharing picker, stops capture immediately and sends a bounded native AI image part only when the user submits it. Installed themes are readable through the native core REST controller; no permanent theme-changing capability is added.
